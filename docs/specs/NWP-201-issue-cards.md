# SPEC · NWP-201 — Issue virtual cards from the console

> Written before any code. Generated with `/spec`, then edited by a human.
> Load it as context when you build: `@docs/specs/NWP-201-issue-cards.md`

**Ticket:** [NWP-201](../tickets/NWP-201.md)
**Author:** Alla Abdella
**Status:** building

## Problem

Ops issues virtual cards by messaging the platform team, who create them by hand. It takes hours, it happens twelve to twenty times a week, and last month two cards went out with the wrong spend limit because the request lived in a Slack thread. Marcus wants the flow in the console: issue a card, see the cards already issued, and open one to check it.

## Current state

There is no card anywhere in the application. `build-battle/merchant-console/CLAUDE.md` says so directly — "Cards is NWP-201 and does not exist yet".

- `src/data/types.ts` — `Currency`, `Merchant`, `Payment`, `Refund`, `Dispute`, `Payout`. No card type. `Payment.amount` carries the comment "Integer minor units. Never a float." and `Payment.createdAt` "ISO 8601, always UTC." New types follow that shape.
- `src/data/store.ts` — `interface Store` holds `merchants`, `payments`, `refunds`, `disputes`, `payouts`, built once by `createStore()` and hung off `globalThis.__northwindStore`. It is a plain mutable object, so a route handler can push to it directly. **There is no write path anywhere in the repository today**; this ticket adds the first one.
- `src/data/generate.ts` — contrary to `merchant-console/CLAUDE.md`, seed data is not JSON. It is generated by a seeded mulberry32 PRNG (`SEED = 20260813`, 120 days), with an injectable-RNG pattern worth copying for card number generation.
- `src/data/queries.ts` — `parseFilters` is the allowlist boundary every route handler calls rather than reading params itself. `paginate<T>` is generic and reusable for cards verbatim. `sortPayments` carries a live defect (see Risks).
- `src/data/merchants.ts` — ten merchants, each with a `currency` and an IANA `timezone`. `merchantById(id)`.
- `src/lib/money.ts` — `formatMoney(minorUnits, currency)` and `parseAmountToMinorUnits(input)`, whose regex `^\d+(\.\d{1,2})?$` already rejects negatives, sub-cent precision and currency symbols. This is the boundary converter for the spend limit; a second one would be a defect.
- `src/lib/dates.ts` — `formatDate` (UTC, for tables), `formatInZone` (merchant timezone, for detail).
- `src/components/Drawer.tsx` — the `@radix-ui/react-dialog` wrapper. **There is no `Dialog.tsx`**, despite `.claude/rules/components.md` naming one. NWP-101's `src/app/payments/export-dialog.tsx` used Drawer; this ticket mirrors it.
- `src/components/ui/payments/StatusBadge.tsx` — one badge for payment, dispute and payout statuses, via three exhaustive `Record<AnyStatus, …>` maps. Card statuses extend it rather than getting a second component.
- `vitest.config.ts` — `include: ["src/**/*.test.ts"]`. A `.test.tsx` is silently skipped, so testable logic must live outside components. Baseline is 28 passing tests across 3 files.

## Domain rules

| Rule | Source | What breaks if ignored |
| --- | --- | --- |
| "Money is integer minor units. `$250.00` is `25000`. No floats, no strings with currency symbols. Format once, at the edge" | `merchant-console/CLAUDE.md` | Limits drift by cents; a limit stored as `"250.00"` cannot be compared |
| "Every generated number starts `4242` and carries a valid Luhn check digit. Nothing here may resemble a real PAN, ever, including in tests and fixtures" | `.claude/rules/cards.md` | The repository ends up holding something that looks like real card data |
| "Generate on the server. A card number produced in the browser is a bug" | `.claude/rules/cards.md` | The number is guessable and the criterion is client-only |
| "Reveal once. The full number appears in the creation response and nowhere else: not on the card record, not in a list or detail payload, not left in client state after the success screen closes" | `.claude/rules/cards.md` | A PAN leaks into every list request |
| "Status is a state machine. `active ⇄ frozen`, either to `cancelled`, and `cancelled` is terminal. Guard the transition on the server, not only in the UI" | `.claude/rules/cards.md` | A cancelled card comes back to life from a crafted request |
| "Validate everything from the client against an allowlist before it reaches the store... Client-side checks are a convenience, never the enforcement" | `.claude/rules/api-routes.md` | A curl bypasses every limit the form imposes |
| "Return the same error shape everywhere: a status code that means what it says, and a body with a message safe to show a user" | `.claude/rules/api-routes.md` | The UI cannot render failures consistently |
| "Storage and bucketing are UTC. Display converts to the merchant's timezone" | `merchant-console/CLAUDE.md` | Created dates shift by a day for London and Berlin merchants |
| "Do not add a database, an ORM, or migrations" | `merchant-console/CLAUDE.md` | Scope explodes into NWP-203 |

## Approach

Split the work so the testable part is pure and the mutable part is thin. `src/lib/cards.ts` holds Luhn, number generation, masking and the spend ratio — no store import, so it is fast to test and lives beside `money.ts` and `dates.ts` as the layout table requires. `src/data/cards.ts` mirrors `queries.ts`: one allowlist gate (`parseCardInput`), the transition table, and the store writes. Route handlers stay flat — validate, call, map an error to a status code — per "reject early and return".

Reveal-once is enforced structurally rather than by discipline: `VirtualCard` has no field capable of holding a full number. The generated number is a local `const` inside `issueCard`, which returns `{ card, number }` as a tuple. Only `POST /api/cards` puts it on the wire, so leaking it from the list or detail route would be a type error rather than something a reviewer has to notice.

Server first. The store, generator, state machine and validation gate are built and proven with curl before a single component exists.

**Considered and rejected:** a Server Action for the create flow. It would be less code, but the repository has no `"use server"` anywhere, and `.claude/rules/api-routes.md` is written against route handlers — which is where validation is expected to live and where it can be proven from a terminal. Explicit routes also make each rejection independently checkable, which is worth more than the lines saved.

**Also rejected:** a second `CardStatusBadge` component. Extending the three `Record` maps in the existing `StatusBadge` is fewer lines and avoids a duplicate helper.

## Plan

1. **Types and store** — done when: `npx tsc --noEmit` is clean with `cards` on the store.
2. **`src/lib/cards.ts` and its tests** — done when: 200 generated numbers all start `4242`, are 16 digits, and pass an independently written `isValidLuhn`.
3. **`src/data/cards.ts` and its tests** — done when: every rejection in the table below has a test, and `cancelled` is proven terminal in all three directions.
4. **Both route handlers** — done when: the routes compile and the store mutates.
5. **Checkpoint: read the whole diff, then run every curl** — done when: five of six core criteria are proven from the terminal, before any component exists.
6. **List page, nav, badge, empty state** — done when: `/cards` renders the written empty state on a cold store.
7. **Issue drawer and reveal screen** — done when: submitting shows the number once and the row appears without a page reload.
8. **Detail page, spend bar, history** — done when: the bar reads "£0.00 of £2,500.00" and the history lists the issue event.
9. **Freeze/unfreeze and cancel-with-confirm** — done when: the badge flips with no page flash and cancelling takes two deliberate clicks.
10. **Amount-sort fix and regression test** — done when: the new test fails on the parent commit and passes on this one.

## Verification

| Acceptance criterion | How it is proven |
| --- | --- |
| Issue a card | `POST /api/cards` returns 201 with the card; the row appears in `GET /api/cards` and on `/cards` |
| Card list at `/cards` | The page renders nickname, merchant, masked number, limit, status and created date; empty state on a cold store |
| Card detail | `/cards/[id]` renders the full record plus spend against limit; unknown id is a 404 |
| Generated numbers | `src/lib/cards.test.ts` checks 200 generations for the `4242` prefix, 16 digits and a valid Luhn digit, verified by a function written independently of the generator |
| Reveal once, mask forever | `POST` response carries `number`; `curl … /api/cards \| grep -c '"number"'` returns 0, and detail `has("number")` is false. The list and detail render `•••• NNNN` |
| Server-side validation | Four curls — unknown merchant, zero limit, limit above 5,000,000, currency `JPY` — each return 400 with a readable message. A limit of exactly 5,000,000 is accepted |
| Status is a state machine | `PATCH` to `frozen`, back to `active`, then `cancelled`; a further `PATCH` to `active` returns 409 |
| Money in minor units | `POST` with `"2,500.00"` stores `250000`; asserted in `src/data/cards.test.ts` as an integer |

## Risks

- **A progress bar wants an inline style**, which `.claude/rules/components.md` forbids, and a template-literal Tailwind class will not survive the JIT scan. Mitigated with a static array of width classes indexed by the ratio rounded to 5%.
- **Radix `Select` has no native label.** Each is paired with `<label htmlFor>` and an `id` on `SelectTrigger`, or the accessibility requirement fails quietly.
- **`src/components/Drawer.tsx` itself uses inline styles and lacks `"use client"`.** Both pre-existing. It is not touched — editing it would risk the NWP-101 export dialog.
- **`sortPayments` in `src/data/queries.ts` compares amounts as text** (`String(a.amount).localeCompare(String(b.amount))`), so `$9.00` sorts after `$10.00`. Pre-existing and unrelated to cards, fixed in its own commit with a regression test so the cards diff stays readable.
- Writes vanish on dev-server restart. That is the store working as designed, not a defect; persistence is NWP-203.

## Out of scope

- Persistence, an ORM, migrations — NWP-203.
- Editing a card's limit after issue — NWP-202.
- Authentication, roles and permissions. `actor` on an audit entry is the constant `"console"` because there is no identity to record.
- Real card network calls. There is no issuer.

## Open questions

- **Spend has no source.** Nothing in the console observes card authorizations, so `spent` is `0` at issue and no code path mutates it. The bar renders that truthfully rather than inventing a number. If spend should be derived from payments on the card's merchant, that is a follow-up and needs a rule for which payments count.
- Whether a card should be blocked when its currency differs from the merchant's settlement currency. `src/data/merchants.ts` carries a currency per merchant, and nothing checks it today. Left out of this ticket deliberately; it wants a product decision about multi-currency merchants rather than a guess.
