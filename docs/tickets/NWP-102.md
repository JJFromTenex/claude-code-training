## Description

Three merchants have reported that the dashboard's daily volume does not match their settlement statement.

Two of them are off by a few cents on high-volume days. The third, a merchant in Berlin, sees an entire day of volume attributed to the wrong date.

Support has not been able to reproduce it reliably, and the pattern is not obvious from the tickets. We do not know yet whether these are one bug or several.

## What we know

- The Berlin merchant is the only reporter outside North America.
- The discrepancy grows with transaction count, which suggests accumulation rather than a single bad record.
- One merchant with heavy refund activity reports totals that look **too high**, not too low.
- Nobody has checked whether the payouts screen agrees with the payments screen.

## What we need first

A written diagnosis before anyone edits code: which files are involved, what the root cause is for each symptom, and which of the three reports share a cause.

Do not fix it in the same session that finds it. Read first.

## Diagnosis (read-only investigation, no code changed)

Surfaced during an unrelated `/ship-ready` pass on NWP-101, then investigated properly with the `bug-investigator` process. All three symptoms live in `src/data/metrics.ts`, but they are **three independent defects, not one bug with three effects** — each has a distinct trigger and none of the fixes for one would touch the others.

**1. Cents drift on high-volume days** — `src/data/metrics.ts:31,34,42-43`
`dailyVolume()` divides each payment's integer minor-unit amount by 100 into a float, accumulates the running sum as a float, then multiplies by 100 and rounds at the end. Binary floats can't represent most cents exactly, so the running sum drifts before the final rounding — more additions (higher volume) means more drift. `src/lib/money.ts:37-43` already has `sumMinorUnits()` for exactly this (sum integers first, divide once at the end); `src/data/analytics.ts` follows that correct pattern elsewhere in the same file family. Confidence: high.

**2. Berlin merchant's day misattributed** — `src/data/metrics.ts:25`
`dailyVolume()` buckets with `new Date(payment.createdAt).toLocaleDateString("en-CA")` — no `timeZone` passed, so it resolves in the server's local time, not UTC, even though the bucket keys themselves (`lastUtcDays()`) are UTC. `src/lib/dates.ts` already has a UTC-correct `utcDayKey()` that isn't used here. This is a real UTC-vs-local bug, but as coded it isn't Berlin-specific — `merchant.timezone` is never read in this function, so it would shift *any* merchant's late-day payments equally, not preferentially Berlin's. Confidence: high that the bug is real; medium that it's the full explanation for a Berlin-specific, one-day report. Still open: the server's runtime timezone (not visible read-only), and whether any screen actually renders a per-merchant daily total for a merchant to compare against their statement — none was found in `overview/`, `payments/`, or `payouts/`.

**3. Refund-heavy merchant sees inflated totals** — `src/data/metrics.ts:53-55`
`headlineMetrics()` computes `grossVolume` as `captured.reduce(...) + refunded.reduce(...)` — adding refunded amounts into a total meant to represent volume processed, instead of netting them out or excluding them, the way `analytics.ts`'s `merchantRollup()` correctly does (captured only). Confidence: high on the mechanics; medium-low on whether this specific aggregate (platform-wide, feeds one stat card on `overview/page.tsx`) is literally what the merchant is comparing against, since it isn't a per-merchant figure as currently built.

**Also noted, not one of the three reported symptoms:** `headlineMetrics()`'s `grossVolume` sums `p.amount` across merchants on different currencies (USD/EUR/GBP) with no conversion, then labels the result `"USD"` — a `money.md` violation ("never sum across currencies"), but a constant platform-wide overstatement, not something that would selectively track with one merchant's refund activity or a single day. Worth its own fix alongside #3 rather than a separate investigation.

**Ruled out:** the payments query builder (`src/data/queries.ts`) and `src/data/analytics.ts`'s weekly rollups/`merchantRollup` — both read clean (integer sums, UTC epoch comparisons, refunds correctly excluded from volume). No shared root cause across the app; the defects are localized to `metrics.ts`.

**Suggested fix, not yet made:**
1. Sum in integer minor units in `dailyVolume()`; divide once at the end, not mid-accumulation.
2. Derive the per-payment bucket key with `utcDayKey()` (`src/lib/dates.ts`), matching how the bucket set itself is built, instead of `toLocaleDateString`.
3. Subtract or exclude `refunded` from `grossVolume` in `headlineMetrics()`, matching `merchantRollup()`.

No `metrics.test.ts`/`analytics.test.ts` exists, which is consistent with these shipping unnoticed.
