Northwind Payments Merchant Console

Architecture notes for build-battle/merchant-console. Current as of NWP-101, which shipped the export options dialog.

What the app does

An internal tool for Northwind's support and ops teams. Staff use it to look up a payment, refund it, and work the dispute queue. Northwind Payments is fictional and every merchant, cardholder, and amount is generated at boot.

/overviewAuthorization, capture, and dispute-free rates, with Summary, Monitoring, and Merchants tabs.
/paymentsFilterable, paginated table of payments. Has the Export button and a detail page per payment.
/disputesThe dispute queue with evidence deadlines.
/payoutsMerchant payouts with gross, fees, and net.

There is no database. Seed data is generated once and held in memory on globalThis so the dev server's hot reload does not reset it. Anything written vanishes on restart, and that is intended. Persistence is a separate ticket, NWP-203.

The four rules

  • Money is integer minor units. $250.00 is 25000. Format once, at the edge, next to its currency code. Helpers in src/lib/money.ts.
  • Storage and bucketing are UTC. Only display converts to the merchant's timezone.
  • One query builder. All payment filtering goes through src/data/queries.ts. A second one is a defect.
  • Validate on the server. Anything from the client is checked against an allowlist before touching a query, filename, or store.

Payments export, end to end

Ops exports the payments table several times a day. Since NWP-101 the Export button opens a dialog first, so the file matches the job instead of being one fixed shape.shipped

1
Filter bar builds the URL src/app/payments/filter-bar.tsx

A client component. Search, status, and merchant selections are pushed into the query string of /payments via the router. Unchanged by NWP-101.

2
Payments page renders the table and the export dialog src/app/payments/page.tsx

A server component. It reads the search params, calls queryPayments for one page of 20 rows, and hands the dialog the query string plus both row counts: the filtered total it already has, and the unfiltered total. The dialog therefore costs no extra request to open.

3
Dialog collects the choices src/app/payments/export-dialog.tsx

Built on the Drawer primitive, which is a Radix dialog, so it has an accessible name, focus handling, and Escape to close. Ten column checkboxes with the card last four unchecked, a scope radio showing the row count for each option, and a Download that turns into a disabled button when nothing is selected. It emits columns as an ordered comma-separated param and scope alongside the existing filters.

4
Route handler validates everything from the client src/app/api/payments/export/route.ts

parseExportColumns checks each name against the allowlist, drops unknowns, collapses duplicates, and keeps the caller's order. An empty or entirely unknown selection returns a 400 with a message safe to show a user, rather than an empty file. parseScope allowlists the two scopes and falls back to the narrower one. parseFilters handles status, sort, and direction as before.

5
Query builder builds the row set src/data/queries.ts

exportRows calls the same filterPayments and sortPayments the table uses, and never paginates. Scope all deliberately drops the active filters. A browser-side export would have shipped only the visible 20 rows, which is the bug this route exists to avoid.

6
CSV helper serializes the chosen columns src/lib/csv.ts

toCsv(rows, columns) writes the header and cells in the order given. EXPORT_COLUMNS is the allowlist of what may be asked for; DEFAULT_EXPORT_COLUMNS is the same list minus the card last four and is what a client that expresses no preference receives. exportFilename(date, scope) stamps both, giving names like payments-disputed-2026-09-10.csv.

7
Response streams back as a download

Content type text/csv with a content-disposition: attachment header carrying the scoped filename.

Known rough edges

Open, and outside the NWP-101 scope
  • Amount sorting compares text, not numbers.open sortPayments in src/data/queries.ts uses String(a.amount).localeCompare(...), so 900 orders after 10000. It affects both the table and the export whenever ops sorts by amount.
  • The amount column carries a currency symbol. The cell renders through formatMoney, so it reads $250.00 while the currency column separately reads USD. Amounts are still integer minor units everywhere upstream and are formatted exactly once, at the edge, so the convention holds. The symbol was left in place because two pre-existing tests pin that output and the test file states that this ticket changes which columns ship, not how a cell is written.
  • There is no Dialog.tsx. .claude/rules/components.md lists one among the available primitives, but src/components/ has only Drawer.tsx. Both wrap @radix-ui/react-dialog, so the export dialog reuses Drawer.
