Northwind Payments Merchant Console

Architecture notes for build-battle/merchant-console. Written for the NWP-101 export options ticket.

What the app does

An internal tool for Northwind's support and ops teams. Staff use it to look up a payment, refund it, and work the dispute queue. Northwind Payments is fictional and every merchant, cardholder, and amount is generated at boot.

/overviewAuthorization, capture, and dispute-free rates, with Summary, Monitoring, and Merchants tabs.
/paymentsFilterable, paginated table of payments. Has the Export button and a detail page per payment.
/disputesThe dispute queue with evidence deadlines.
/payoutsMerchant payouts with gross, fees, and net.

There is no database. Seed data is generated once and held in memory on globalThis so the dev server's hot reload does not reset it. Anything written vanishes on restart, and that is intended. Persistence is a separate ticket, NWP-203.

The four rules

  • Money is integer minor units. $250.00 is 25000. Format once, at the edge, next to its currency code. Helpers in src/lib/money.ts.
  • Storage and bucketing are UTC. Only display converts to the merchant's timezone.
  • One query builder. All payment filtering goes through src/data/queries.ts. A second one is a defect.
  • Validate on the server. Anything from the client is checked against an allowlist before touching a query, filename, or store.

Payments export, end to end

Today the export is a plain link. There is no dialog, no column choice, and no scope choice. This is what NWP-101 changes.

1
Filter bar builds the URL src/app/payments/filter-bar.tsx

A client component. Search, status, and merchant selections are pushed into the query string of /payments via the router.

2
Payments page renders the table and the Export link src/app/payments/page.tsx

A server component. It reads the search params, calls queryPayments for one page of 20 rows, and renders an Export button that is just an anchor to /api/payments/export? plus the same query string.

3
Export route handler parses and validates the filters src/app/api/payments/export/route.ts

Calls parseFilters, which allowlists status, sort, and direction and sanitizes the page number. Then it calls filterPayments and sortPayments directly, skipping pagination, so the whole filtered set is exported.

4
Query builder filters the in-memory store src/data/queries.ts

filterPayments applies status, merchant, date range, and a text search over id, description, last four, and merchant name. sortPayments orders by date or amount.

5
CSV helper serializes the rows src/lib/csv.ts

toCsv already accepts a columns argument, but the route never passes one, so every export includes all ten columns from EXPORT_COLUMNS, including last4. exportFilename produces payments-YYYY-MM-DD.csv with no scope.

6
Response streams back as a download

Content type text/csv with a content-disposition: attachment header. The browser saves the file.

Where NWP-101 plugs in

  • Dialog on the page. Replace the anchor with a client component using the existing Dialog primitive. Column checkboxes with last4 off by default, a scope radio for current filter or all payments, and a row count fetched from GET /api/payments, which already returns total.
  • Route handler. Accept columns and scope params. Validate columns against EXPORT_COLUMNS before use. For all payments, call filterPayments with empty filters. Pass the validated column list to toCsv.
  • CSV helper. Extend exportFilename to take a scope label. Add tests to the existing csv.test.ts.
Two things worth knowing before you start
  • The amount CSV cell uses formatMoney, which adds a currency symbol and thousands separators. The ticket asks for amounts formatted once with currency in its own column, so the amount column probably wants a plain decimal instead.
  • sortPayments sorts by amount using string comparison, so 900 sorts after 10000. Not part of NWP-101, but it affects export order when sorting by amount.
